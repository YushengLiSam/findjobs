# 生成物缓存 — 复用协议

所有**自由文本类**的生成结果都缓存在这里，按「字段类型 × 岗位family」做 key。
目的：同类岗位不从零生成，只做**增量微调**。

## 目录

```
generated/
  index.json          key → 文件路径 的索引，先查这个
  self-eval/          自我评价 / 个人优势 / 个人简介
  qa/                 自定义问答（为什么选我们、职业规划、最有成就感的事…）
```

## Key 的构成

```
<字段类型>/<岗位family>
```

**岗位family 取值**（固定这几个，不要临时造新的）：

| family | 涵盖岗位 |
|---|---|
| `ai-agent-llm` | AI Agent 研发、LLM 应用、大模型应用开发、Agent 架构 |
| `algorithm` | 算法工程师、机器学习、NLP、CV、推荐 |
| `backend` | 服务端研发、后端开发、Java/Go/Python 后端 |
| `fullstack` | 全栈、应用开发 |
| `infra` | 基础架构、平台开发、中间件、云原生 |
| `data` | 数据开发、数据平台、数据分析 |

判断方法：读 JD 的**职责部分**（不是任职要求），看主体工作是什么。同一个 JD 可能横跨两个 family，取权重最大的那个；两个都很重就以主 family 为基底，从次 family 的缓存里借 1-2 段。

## 复用流程（每次投递必走）

```
1. 读 JD → 判定 family
2. 查 generated/index.json 有没有该 key
   ├─ 命中 → 读缓存文件 → 走【微调】
   └─ 未命中 → 走【新建】
3. 填入表单
4. 回写缓存（无论命中与否都要写，见下）
```

### 【微调】命中缓存时

**self-eval 已改为「骨架 + 第3段变体」结构**（2026-09-05），流程是：

1. 读 JD 职责部分，提炼这家最在意什么
2. 从 `self-eval/_HOWTO-fewshot.md` 的**立论库**挑一条最契合的
3. 取缓存文件里该立论对应的**骨架**：段1/段2/段4 基本不动
4. **只写段3**（适配这家的业务特性）
5. 写完把段3 追加进缓存文件的「第3段变体表」
6. 过 `_HOWTO` 的硬性检查清单

**为什么不再"整篇微调"**：旧做法是保留一份正文、每次改一改，
结果基底永远变成最后投的那家（曾漂移成摩尔线程「财务ERP」版），
下一个泛 Agent 岗命中缓存反而要往回改。骨架分立论存，就不会漂。

命中缓存时这一步应在 **1-2 分钟内**完成，不要重新读简历。

⚠️ **无论重合度多高，段3 都要重写**，绝不能出现上一家公司的名字。

### 【新建】未命中缓存时

按 `profile/answer_bank.md` 里「自由文本类的写法原则」生成，然后**立刻建缓存文件**。

## 回写规则（不能省）

每次投完，无论命中与否：

- **命中且只做了微调** → 在缓存文件的「变体记录」里追加一行（日期/公司/岗位/改了什么），正文不动
- **命中但改动很大**（超过三成内容） → 把新版设为该 family 的正文，旧版移入「历史版本」
- **未命中** → 新建 `<family>.md`，并在 `index.json` 加一条

## 缓存文件格式

每个 `self-eval/<family>.md` 必须含这四块：

```markdown
# 自我评价 · <family>

## JD 关键词（本正文针对的）
用于下次比对差集

## 主推经历
经历库里的编号，如 R1 + R2 + P1 + I1

## 正文
（可直接粘进表单的文本）

## 变体记录
| 日期 | 公司 | 岗位 | 改动 |
```

## 重要边界

缓存的是**表达方式**，不是事实。复用时事实必须仍然为真：

- 论文状态会变（在投 → 接收 / 被拒），引用前核对 `candidate_profile.json`
- 「至今」类经历的时间跨度会变
- **绝不因为缓存里这么写过就沿用一个已经不准确的说法**
