## 骨架 A · 立论「评测体系要先于优化存在」

**适用**：效果向岗位、AI 应用落地岗、JD 里出现「评测/指标/效果/迭代」

**段1**
> 我做 AI 研发有一个基本判断：评测体系必须先于优化存在，否则"变好了"只是错觉。

**段2**
> 这个判断来自真实项目中的反复验证。做工业智能体评测时，我看到同一个任务在工具调用和文本检索架构下会出现完全不同的可靠性；做电商导购 Agent 时，我发现 Prompt 无法稳定守住否定约束和事实边界，于是把关键约束下沉为确定性代码，并在上线前用评测集与对抗测试主动寻找失效点；做搜索型终端 Agent 时，我又意识到长程任务的瓶颈往往先出现在状态管理，而不只是模型推理能力。

**段3** → 见下方变体表

**段4**
> 工作方式上，我依赖数据而不是感觉，习惯把研究原型做成可复现、可部署、可验证的系统；性格上乐于协作、主动补位，能适应快速迭代。

## 骨架 B · 立论「复杂工作流的上限取决于状态可见、工具受约束、结果可评测」

**适用**：Agent 平台、工作流编排、多模态长链路、JD 里出现「编排/工作流/可观测」

**段1**
> 我做 Agent 有一个判断：复杂工作流的上限不只取决于模型能力，更取决于状态是否可见、工具是否受约束、结果是否可评测。偶尔答对不等于能进生产，系统还必须可观测、可恢复。

**段2**
> 这个判断来自不同实践。工业智能体评测让我看到，MCP 工具调用与文本 RAG 会产生不同的失败模式；搜索型终端 Agent 让我意识到，长任务常先卡在上下文、状态分支和回滚；电商导购与电力策略系统则让我把检索、结构化输出、确定性校验、人工确认和对抗测试放进同一工作流，主动寻找失效点。

**段3** → 见下方变体表

**段4**
> 工作方式上，我习惯先定义失败模式、观测信号和恢复策略，再抽象公共组件并补齐测试与文档；也会用小规模实验快速验证方案，关键逻辑和结论必须由代码与数据复核。性格上乐于协作、主动补位。

## 骨架 C · 立论「大模型不能被信任，必须用确定性的东西兜住」

**适用**：金融、医疗、工业、企业内部系统、JD 里出现「合规/权限/审计/可追溯」

**段1**
> 我做企业级 AI 应用有一个判断：答案是否流畅不是第一位，数据口径、权限边界和结论可追溯性是否正确，才决定系统能否真正进入业务流程。

**段2**
> 这个判断来自几类实践。工业智能体评测让我看到，同一任务在工具调用和文本检索架构下会暴露不同的失败模式；电商导购项目让我把混合检索、重排、来源标注、规则约束与回归评测放进一条链路；电力策略系统则让我坚持让 LLM 只生成结构化数据，再由确定性逻辑完成校验、确认与审计。

**段3** → 见下方变体表

**段4**
> 工作方式上，我习惯把需求理解、Python/SQL 实现、测试文档和效果复盘连成闭环；性格上主动负责、乐于沟通。
